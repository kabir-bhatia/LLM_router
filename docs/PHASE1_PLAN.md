# Phase 1 plan: the 8-category eval dataset

**Goal:** a dataset of tasks with gold answers that every later number depends on: the
16-model benchmark, the routing policy, the classifier accuracy and the final cost/accuracy
result. If the gold answers are wrong or the tasks are too easy, every later result is wrong too.

**Output:** `eval/tasks_8cat.json` (400 tasks: 50 per category), a dev/test split, a grader per category, and
self-tests that prove each grader works.

**Effort:** about 2 days. **API spend:** ~$0 (Phase 1 builds and checks data; it calls no models).

## 1. Task format

One JSON record per task:

```json
{
  "id": "math-017",
  "category": "math",
  "prompt": "A warehouse holds 1,250 boxes ...",
  "gold": {"answer": 830, "tolerance": 0.01},
  "grader": "numeric",
  "source": "generated:percent_chain",
  "difficulty": "medium",
  "phrasing": "word_problem",
  "split": "dev",
  "note": "why this gold answer is right, in one line"
}
```

`phrasing` records the style of the prompt (formal, casual, imperative, embedded in a longer
message...). The classifier is tested on it, so prompts must not all start with the same keyword.

## 2. Where the tasks come from, per category (50 each)

Three sources, chosen per category for **correct gold answers** and **no memorised answers**:
- **Generated by code:** the answer is computed, so it's provably right, and the exact problem has never been seen online.
- **Written fresh:** drafted, then reviewed by you.
- **Adapted from public datasets:** reworded, with the licence noted. Used only where hand-writing gold answers is error-prone.

| Category | Source | Gold answer | Grader |
|---|---|---|---|
| **Math** | Generated: templates for percentages, multi-step arithmetic, ratios, growth/projections, unit rates, with random numbers | Computed by the generator | Number match with tolerance |
| **Logic** | Generated: assignment puzzles (people × items) and ordering puzzles, 3–5 entities. A brute-force solver keeps only puzzles with **exactly one** solution | The unique solution | Exact match of the asked-for value |
| **Sentiment** | Written fresh: reviews, tweets, support messages; balanced across positive / negative / mixed / neutral, including sarcasm and "but" cases | Label + a short reason | Label match (the reason only needs to be present) |
| **NER** | Written fresh: sentences with PERSON / ORG / LOCATION / DATE, including tricky ones (org named after a person, dates written several ways) | Set of (entity, type) | Entity-level F1; pass at F1 = 1.0 (tolerant to case, spacing and date format) |
| **Code debugging** | Written fresh: Python functions with one planted bug each (off-by-one, wrong operator, mutable default, wrong base case...) | Hidden unit tests | Pull the fixed function out of the answer and run the tests in a subprocess with a timeout |
| **Code generation** | Written fresh: short function specs, style of MBPP but new | Hidden unit tests (5–8 each, edge cases included) | Same test runner as debugging |
| **Summarisation** | Written fresh: 120–250-word passages with an explicit constraint (one sentence / ≤ N words / exactly 3 bullets) | Constraint + 2–4 key facts that must survive | Code checks the constraint; the blind judge checks the facts and flags invented ones |
| **Factual** | Written fresh: "explain / define / how does X work" questions, spread over science, tech, history, finance | Reference answer + 2–3 key points | Blind judge against the reference (pass/fail) |

**Difficulty mix per category:** about half `easy`, half `hard` (D9 routes per category × difficulty, so both cells need enough items). Every task carries the label. Without hard items every model
passes, and the benchmark can't tell the models apart. The smoke test already shows the spread:
small models get the simple math right but fail a 3-person logic puzzle.

## 3. Answer-format instruction (decided now, used in every later phase)

Every model, local or paid, gets the same short system prompt for each category, e.g.
"End with a final line `ANSWER: <value>`" for math, logic and sentiment; "Return only JSON" for NER;
"Return only the corrected function in one code block" for debugging. Same instruction for all 16
models, so the comparison is fair. Graders read that line or block, with a lenient fallback.
This also keeps paid output tokens down later.

## 4. Graders (`eval/graders/`)

- `numeric.py`, `exact.py`, `label.py`, `ner_f1.py`, `code_tests.py` (subprocess sandbox, 5 s timeout, no network), `constraint.py` (sentences / words / bullets), `judge.py` (blind Qwen judge; only a stub in Phase 1).
- **Self-tests:** each grader gets known-good and known-bad answers (taken from the smoke-test outputs where possible, such as `qwen2.5-coder`'s "150" for the 270 problem) and must score them correctly. `pytest eval/graders` must pass before Phase 2.

## 4b. How gold answers are verified at 50 per category (D3)

| Category | Verification |
|---|---|
| Math | Generated; answer re-computed by a second, independent code path |
| Logic | Generated; brute force confirms exactly one solution |
| Code debugging | Reference fix + unit tests: tests must **pass** on the reference and **fail** on the buggy version |
| Code generation | Reference solution must pass all tests (5–8 per task, edge cases included) |
| NER | Mostly built from templates with known slots (gold by construction) + ~15 tricky hand-written items |
| Sentiment, factual, summaries | Claude drafts item + gold; GLM 5.3 Flash (Hyde, free) answers independently; agreements are spot-checked (20% sample), **disagreements go to Kabir** |

**Solver anti-overfitting (D7):** math and logic use two separate template sets. Set A is used while
building the Phase 4 solvers; the test split uses only set B plus 10–15 hand-written items per category.

## 5. Quality checks before the dataset is accepted

1. **Gold-answer check:** generated items are re-solved independently by a second code path; written items' unit tests must pass against a reference solution.
2. **Uniqueness:** every logic puzzle has exactly one solution (brute force).
3. **No duplicates:** no two prompts are near-duplicates (embedding similarity ≥ 0.95 is flagged).
4. **Your review:** you read every item where Claude and GLM disagree, plus a 20% random sample of the rest, in batches. Each item has a `note` explaining the answer so you can defend it. This is the lesson from Phase 2 of the old project.
5. **Split:** 60% dev / 40% test, stratified by category and difficulty, fixed seed. The test split is not opened until Phase 6.
